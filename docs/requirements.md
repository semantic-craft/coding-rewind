文档里用三种标记，避免把转述写成已经拍板的决定：

- **决定**：用户已明确说出的要求。
- **方向（转述）**：讨论中已形成的产品方向，但原文是转述，不是逐字引用。
- **建议**：调研或整理时提出的做法，用户尚未确认。
- **待决**：需要用户再决定的事项。

**关于核心痛点、时间尺度（1～3 天近期暂存）、双来源场景与服务于写作/思考：**

> 我们这个项目实际上要解决这么一个问题，比如说我们在用Coding Agent的时候呢，经常会遇到一些片段，这些片段下意识地会觉得以后有用。 一两天内马上会用到，但是暂时又不想为这个去存到notes里面，其实一种方法是存到备忘录，但感觉总不太好。 所以我脑袋中总设想说有没有可能这个东西是我马上可能两三天后马上要用的。 这个Notes都保留进去。简单来讲就是我有一些片段我以后是用得上的。我希望我能够有这些东西能够回顾。有些时候呢，大多数时候 有些时候可能又是在单独的app里面，比如说网页版的聊天记录啊。 两种情况，一种是在Coding Agent的桌面版，一种是在网页版。他们都有对话，偶尔有一些片段会给我带来一些灵感，我会想要保留它们，然后偶尔还想要互动 每个目的就是说最后写东西的时候思考的时候要用得上。

## 已记录的产品方向

- **标记**：方向（转述）
- **日期**：2026-11-09（立项说明中的「昨日讨论」；今天整理时为 2026-11-10）
- **说明**：以下不是用户逐字原话，是立项时保留的方向摘要。设计 MVP 时按此理解，但若用户日后给出更精确的原话，应改正文并保留日期。

1. 选段一键留存：由用户选中片段后保存，而不是先做全量采集。
2. 不强迫标题、标签：保存时可以不填；标题和标签若存在，只能是可选补充。
3. 保留原问题、原文、出处：片段不能只剩一句摘录，必须能回到当时的问题、完整被保存的原文，以及来源信息。
4. 自然语言找回：事后可以用平常的说法把片段找回来，而不只依赖精确关键词或预先打好的标签。

## MVP（结合 2026-11-10 一手决定与已记录方向更新）

- **标记**：建议（其中带用户一手要求的条目承接上方「决定」，具体交互与实现切分仍可在编码前调整）

MVP 聚焦「在 Antigravity App 2.x 与网页聊天中零打扰顺手暂存好段落 → 在近 2～3 天热窗口中回顾找回 → 围绕片段互动推演并辅助成文」：

1. **双场景零打扰一键暂存**：用户在 **Google Antigravity App 2.x** 或受支持的 **网页版 AI 聊天** 中选中一段有用的回答、提示词或思路，用一次明确操作即可暂存；**不打断当前对话、不强迫当场开新对话、不必先填标题或标签**。
2. **保留语境与出处**：每条记录至少保存选中的原文、对应的原问题（若当时能取到；取不到时如实标明缺失，不编造），以及出处（来源应用/站点、会话或项目标识、可打开的链接或协议定位，以及保存时间）。
3. **近期热窗口回顾与自然语言找回**：默认突出展示最近 2～3 天（及近期）暂存的灵感卡片流，方便快速扫读重温；同时支持按自然语言找回已保存片段，并查看原文、原问题与出处。
4. **围绕片段互动与成文（A + C）**：用户可勾选一或多条暂存片段，围绕它们继续与 AI 追问、碰撞推演（A），并能在对照这些片段的同时撰写草稿或思考笔记、由 AI 辅助整理（C），既可通过本机原生工作台完成，也可通过本地 MCP 与 Skill 接入 Antigravity App（如其 `Knowledge Work` 界面）。
5. **数据可控**：用户可以导出自己保存的数据，也可以删除单条或全部数据。原则见 [privacy.md](privacy.md)。

MVP 不要求：多端云同步、账号系统、全量自动采集、相关时主动弹窗提示、社区分享，或一次性适配市面上所有聊天客户端。

## 非目标（当前）

- **标记**：决定与建议的混合；其中带「本轮」的是已授权范围，其余是为防止范围膨胀而写下的建议，实施前若用户明确要求可以再开。

当前明确不做：

- 本轮写功能代码、构建、部署、初始化 git、创建远端仓库或推送。
- 把本项目做成 process / 项目管理工具。
- 默认全量采集全部聊天记录。「自动暂存」若以后进入范围，也需要单独决定，不能从 MVP 里偷运进来。
- 在文档或外部服务中上传、粘贴真实私密聊天。
- 把商业产品（如 Glasp、Superpower ChatGPT）当成开源实现来复制。
- 抄录第三方源代码。
- 在仅文档与抛弃式原型阶段提前向本仓库塞入空源码树或未定稿构建脚本。
- 设计必须依赖云端账号、重型容器服务（如 Docker 数据库集群）或半原生半 WebView 胶水层才能运行的方案。

## 待决事项

需要用户之后明确选择的问题（不要由文档或 agent 擅自填成决定）：
